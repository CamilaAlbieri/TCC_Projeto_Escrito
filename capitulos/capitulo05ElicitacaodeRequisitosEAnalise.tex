\chapter{Elicitação de Requisitos e Análise}
\label{cap:05}
A engenharia de requisitos é uma etapa fundamental no processo de desenvolvimento de software, sendo responsável por definir o que o sistema deve fazer e sob quais restrições ele deve operar \cite{Valente2020}. 
Segundo \cite{Sommerville2011}, essa disciplina engloba as atividades de descoberta, análise, documentação e validação dos requisitos, constituindo a base sobre a qual todo o projeto será construído.
\cite{pressman2016} complementam essa visão ao afirmar que a engenharia de requisitos envolve a coleta de informações sobre o sistema a ser desenvolvido, a análise do problema e a descrição, classificação e priorização dos requisitos identificados.

O processo de elicitação de requisitos, também chamado de levantamento ou descoberta de requisitos, consiste em reunir informações junto aos stakeholders para compreender suas necessidades e expectativas em relação ao sistema \cite{Sommerville2011}.
Diversas técnicas podem ser empregadas nessa etapa, como entrevistas, questionários, workshops, prototipação e análise de cenários de uso \cite{Valente2020}

Este capítulo apresenta os requisitos identificados para o sistema proposto, organizados em requisitos do usuário e requisitos do sistema, sendo estes últimos subdivididos em requisitos funcionais e não funcionais.


\section{Requisitos do Usuário}

Requisitos de usuário são declarações, em linguagem natural com diagramas, dos serviços que o sistema deverá fornecer aos seus usuários e das restrições com as quais ele deve operar \cite{Sommerville2011}. \citeauthorandyear{pressman2016} destacam que um documento de requisitos de sistema precisa ser claro, consistente e completo, pois servirá de referência para desenvolvedores, gerentes de projeto e engenheiros de testes ao longo de todo o ciclo de vida do software.

Antes de apresentar os requisitos propriamente dito, é importante compreender quatro conceitos centrais que estruturam a forma como os dados do sistema se relacionam: \textbf{Widget}, \textbf{Layout}, \textbf{Item} e \textbf{ItemWidget}. Esses elementos operam em conjunto para oferecer ao usuário a experiência de personalização que caracteriza a plataforma.

No contexto deste projeto, os requisitos do usuário foram identificados com base nas necessidades de organização e personalização de coleções pessoais. Uma analogia útil é a de um \textbf{formulário e suas respostas preenchidas}. O \textit{Layout} funciona como um formulário em branco, definindo quais campos existem, sua posição visual e seu tamanho. Os \textit{Widgets} correspondem aos campos propriamente ditos, como uma caixa de texto, um seletor de estrelas para classificação, um campo para imagem, entre outros. Um \textit{Item} representa uma resposta preenchida desse formulário, associada a um conteúdo específico do acervo do usuário, como um livro ou filme. Por fim, o \textit{ItemWidget} é a entidade que armazena, para cada item, o valor que o usuário forneceu em cada campo --- isto é, a ponte entre a estrutura do formulário (Layout e Widgets) e os dados efetivamente informados pelo usuário (Item).

Em termos práticos, considere um exemplo concreto. Suponha que a usuária crie um Layout chamado \textit{``Card de Livro''} contendo quatro widgets: 
um de \textit{Imagem} para a capa, um \textit{Input Field} para o autor, um widget de \textit{Classificação} de um a cinco estrelas e uma área de \textit{Texto} para notas pessoais. Cada widget possui posição e tamanho próprios dentro da área de edição do layout. Ao cadastrar o item \textit{``Duna''}, o sistema gera automaticamente os registros de ItemWidget correspondentes: para o widget \textit{Imagem}, armazena o arquivo da capa; para o widget \textit{Input Field}, armazena o texto \textit{``Frank Herbert''}; para o widget \textit{Classificação}, o valor \textit{5}; e para o widget \textit{Texto}, a nota \textit{``Obra-prima do gênero''}. Desse modo, o Layout e seus Widgets permanecem inalterados e podem ser reutilizados por centenas de itens, enquanto cada item mantém seus próprios valores por meio dos registros de ItemWidget.

Essa separação traz três benefícios diretos para o projeto: 

(i) permite que o usuário reutilize o mesmo layout para múltiplos itens sem duplicação de estrutura; 

(ii) viabiliza que cada item preserve valores distintos, respeitando a individualidade de cada obra cadastrada; e 

(iii) permite modificações individuais em um item específico --- por exemplo, adicionar um widget extra apenas a um único livro --- sem afetar o layout original nem os demais itens (RF-12).

\subsection{Organização em Pacotes}
\label{subsec:pacotes_dominio}

Devido à quantidade de classes conceituais envolvidas, o modelo de domínio foi organizado em cinco pacotes, de modo a agrupar entidades que compartilham propósito semântico e reduzir a complexidade visual do diagrama. Essa segmentação segue a recomendação de \cite{Larman2007}, segundo o qual o agrupamento de classes em pacotes facilita a leitura do modelo, evidencia suas fronteiras conceituais e favorece o raciocínio modular sobre o sistema. Os pacotes adotados neste trabalho são:

\begin{itemize}[nosep,leftmargin=1.5em,topsep=4pt,partopsep=0pt,
               parsep=2pt,itemsep=4pt]

  \item \textbf{Usuário} --- concentra a entidade central da plataforma,
  responsável pelos dados de identificação e pelo vínculo com todas as demais
  entidades do sistema. Foi isolada em um pacote próprio por atuar como ponto
  de referência para os demais agrupamentos.

  \item \textbf{Coleções} --- reúne as entidades que compõem a estrutura de
  organização do acervo em três níveis hierárquicos: Categoria, Coleção e
  Item. Inclui também a entidade associativa ItemWidget e a enumeração de
  privacidade. Representa o núcleo de domínio da aplicação, pois é nele que
  o usuário efetivamente cadastra e organiza seu conteúdo.

  \item \textbf{Editor de Layout} --- agrupa as entidades responsáveis pela
  personalização visual das fichas de itens, incluindo Layout, Widget e a
  enumeração de tipos de widget. É este pacote que sustenta o diferencial de
  customização da plataforma.

  \item \textbf{Interação Social} --- concentra as entidades ligadas aos
  vínculos entre usuários, como as solicitações de amizade (Amizade e
  StatusAmizade) e o acompanhamento de categorias de outros usuários
  (Seguir Coleção).

  \item \textbf{Notificações} --- reúne as entidades responsáveis pelo
  registro e pela exibição de eventos relevantes ao usuário: a própria
  entidade Notificação, a enumeração TipoNotificacao, a entidade
  AtualizaçãoEvento e a enumeração TipoEvento. A separação deste pacote
  em relação ao de Interação Social reflete a distinção entre o vínculo
  social em si e o mecanismo de comunicação dessas ocorrências ao usuário,
  além de isolar a lógica de geração e exibição de notificações para
  facilitar futuras extensões do sistema.

  \item \textbf{Aparência} --- reúne as entidades que definem a configuração
  visual global da interface, como paletas de cores, tipografia e seleção de
  tema claro ou escuro.

\end{itemize}

Essa organização reflete a separação de responsabilidades identificada durante
a elicitação de requisitos: as classes do pacote \textit{Coleções} sustentam
os requisitos funcionais de gestão de conteúdo (RF-04 a RF-09); as do pacote
\textit{Editor de Layout} suportam os requisitos de personalização estrutural
(RF-10 a RF-12); as do pacote \textit{Aparência} viabilizam a personalização
visual global (RF-13 e RF-14); as do pacote \textit{Interação Social} dão
suporte às funcionalidades de rede entre usuários (RF-15 e RF-16); e as do
pacote \textit{Notificações} sustentam o mecanismo de comunicação de eventos
do sistema ao usuário (RF-17 e RF-21).
A Figura~\ref{fig:ModeloDominio} apresenta o modelo de domínio desenvolvido neste trabalho, evidenciando a organização em pacotes descrita acima, bem como as 
principais classes conceituais do sistema e as associações que estabelecem entre si.



\section{Requisitos do Sistema}

\citeauthorandyear{Sommerville2011} afirma que os requisitos do sistema são tradicionalmente classificados em requisitos \textbf{funcionais}, que descrevem as funcionalidades que o sistema deve oferecer, e requisitos \textbf{não funcionais}, que definem restrições de qualidade como desempenho, segurança e usabilidade. Eles constituem o núcleo da especificação do sistema, pois delimitam o escopo das funcionalidades a serem implementadas, e sua classificação permite uma organização sistemática das especificações, facilitando tanto o desenvolvimento quanto a validação do sistema.

Assim, esta seção apresenta os requisitos identificados neste trabalho, organizados nas subseções a seguir.


\subsection{Requisitos Funcionais}

Segundo \citeauthorandyear{Sommerville2011}, requisitos funcionais descrevem as funções ou serviços que o sistema deve fornecer, ou seja, o que o sistema deve fazer. Eles especificam as ações que o sistema deve ser capaz de executar em resposta a entradas específicas ou em determinadas condições.

Os atores que interagem com o sistema são: \textbf{Usuário}, que representa a pessoa cadastrada na plataforma e responsável por criar, editar e gerenciar suas categorias, coleções, itens e interações sociais; e o \textbf{Sistema}, que atua de forma autônoma em funcionalidades como exibição de fichas de itens, envio de notificações, atualização do feed em tempo real e organização visual dos dados.

Para padronizar a especificação dos requisitos, adotou-se o verbo \textbf{gerenciar} como forma genérica de representar operações do tipo CRUD (cadastrar, editar e excluir), sempre que aplicável. Essa padronização reduz a repetição textual e torna a descrição dos requisitos mais objetiva.

Os requisitos funcionais estão organizados em grupos e apresentados de forma sequencial, seguindo uma ordem lógica de dependência entre funcionalidades: iniciam pelos requisitos de acesso ao sistema (cadastro, autenticação e gerenciamento de perfil), prosseguem com a estrutura central do sistema (categorias, coleções, itens e suas fichas), seguem com o editor de layouts e widgets, avançam para a personalização visual global, para as funcionalidades sociais (amizade, acompanhamento de categorias e feed) e culminam com a tela principal e o gerenciamento de notificações. 
Os quadros~\ref{quad:descricao_campos} a~\ref{quad:atores} apresentam a definição dos campos e das classificações utilizadas na especificação, e os requisitos funcionais identificados para este sistema estão apresentados nos Quadros~\ref{quad:rf01} a~\ref{quad:rf21}.

\subsection{Requisitos Não-Funcionais}
Segundo \citeauthorandyear{Sommerville2011}, os requisitos não funcionais são requisitos que não estão diretamente relacionados com os serviços específicos oferecidos pelo sistema a seus usuários.
Logo, não dizem respeito diretamente às funcionalidades fornecidas pelo sistema, mas sim às suas propriedades e restrições de qualidade.
\citeauthorandyear{Pressman2016}, dizem que esses requisitos especificam atributos como desempenho, usabilidade, segurança, confiabilidade e portabilidade, sendo fundamentais para garantir que o sistema atenda aos padrões de qualidade esperados.
Assim, esta seção apresenta os requisitos não-funcionais identificados neste trabalho, consolidados nos Quadros de ~\ref{quad:rnf01} a ~\ref{quad:rnf10}.

Essa separação permite que o usuário organize seu acervo em duas camadas antes de cadastrar qualquer item, facilitando a categorização e a personalização por meio de layouts em níveis distintos.

Nome do Caso de Uso & Gerenciar Solicitações de Amizade \\ \hline

Descrição Resumida & Este caso de uso permite que o usuário visualize, aceite ou recuse solicitações de amizade recebidas de outros usuários da plataforma. Ao aceitar, o vínculo de amizade é criado mutuamente. Ao recusar, a solicitação é marcada como recusada e o solicitante é notificado (RF-15 e RF-21). \\ \hline

Fluxo Básico & \mbox{}
\textbf{FB01:} Aceitação de solicitação de amizade
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item O usuário acessa a área de notificações ou de solicitações pendentes.
    \item O sistema exibe a lista de solicitações de amizade com status ``pendente'', contendo nome, foto e data de envio de cada solicitante.
    \item O usuário seleciona a solicitação desejada e clica em ``Aceitar''.
    \item O sistema atualiza o status da solicitação para ``aceita'' no banco de dados.
    \item O sistema cria o vínculo de amizade mútuo entre os dois usuários.
    \item O sistema envia notificação ao solicitante informando que a solicitação foi aceita [include: Gerenciar Notificações do Sistema].
    \item O sistema exibe mensagem de sucesso: ``Vocês agora são amigos!''
    \item O sistema atualiza a lista de solicitações, removendo a solicitação aceita.
\end{enumerate}
\mbox{} \\ \hline

Fluxos Alternativos & \mbox{}
\textbf{FA01:} Recusa de solicitação
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 3 do FB01, o usuário clica em ``Recusar'' na solicitação desejada.
    \item O sistema atualiza o status da solicitação para ``recusada'' no banco de dados.
    \item O sistema notifica o solicitante de que a solicitação foi recusada (RF-21).
    \item O sistema remove a solicitação da lista de pendentes do usuário.
    \item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA02:} Nenhuma solicitação pendente
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 2 do FB01, o sistema identifica que não há solicitações pendentes.
    \item O sistema exibe mensagem: ``Você não possui solicitações de amizade pendentes.''
    \item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA03:} Solicitação cancelada pelo remetente
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 3 do FB01, o usuário tenta aceitar uma solicitação que foi cancelada pelo remetente antes da resposta.
    \item O sistema exibe mensagem: ``Esta solicitação não está mais disponível.''
    \item O sistema remove a solicitação da lista de pendentes.
    \item O caso de uso é encerrado.
\end{enumerate}
\mbox{} \\ \hline

Requisitos Especiais & RNF08 - Notificações de aceite/recusa devem ser enviadas em tempo real. RNF02 - A operação deve ser concluída em até 3 segundos. \\ \hline

Condições Prévias & O usuário deve estar autenticado. Deve existir ao menos uma solicitação de amizade com status ``pendente'' endereçada ao usuário. \\ \hline

Pós-Condições & Se aceita: vínculo de amizade mútuo criado; ambos os usuários aparecem na lista de amigos um do outro. Se recusada: status da solicitação atualizado para ``recusada''; nenhum vínculo é criado. Em ambos os casos, o solicitante é notificado (RF-21). \\ \hline

Pontos de Extensão & Nenhum ponto de extensão identificado para este caso de uso. \\

Nome do Caso de Uso & Visualizar Perfil de Amigo \\ \hline

Descrição Resumida & Este caso de uso permite que o usuário acesse o perfil público de um amigo confirmado, visualizando suas informações básicas e as categorias disponíveis conforme o nível de privacidade configurado pelo dono. A navegação nas categorias, coleções e itens do amigo é restrita ao modo somente leitura (RF-18 e RF-19). \\ \hline

Fluxo Básico & \mbox{}
\textbf{FB01:} Visualização do perfil de amigo
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item O usuário acessa a lista de amigos ou realiza busca pelo nome do amigo.
    \item O usuário seleciona o amigo desejado.
    \item O sistema recupera as informações públicas do perfil do amigo (nome, foto, biografia).
    \item O sistema recupera as categorias do amigo com privacidade ``pública'' ou ``somente amigos''.
    \item O sistema exibe o perfil do amigo com suas informações e as categorias acessíveis.
    \item Categorias com privacidade ``privada'' não são listadas nem mencionadas.
    \item O usuário navega pelas categorias visíveis e, dentro delas, pelas coleções e itens, em modo somente leitura.
    \item O usuário pode optar por seguir uma categoria visível [E01].
\end{enumerate}
\mbox{} \\ \hline

Fluxos Alternativos & \mbox{}
\textbf{FA01:} Amigo sem categorias acessíveis
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 4 do FB01, o sistema identifica que todas as categorias do amigo são privadas ou que ele não possui categorias.
    \item O sistema exibe o perfil básico do amigo com a mensagem: ``Este usuário não possui categorias públicas no momento.''
    \item O caso de uso continua sem exibir categorias.
\end{enumerate}

\textbf{FA02:} Tentativa de acesso a categoria privada por link direto
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item O usuário tenta acessar uma categoria privada de um amigo por meio de link direto.
    \item O sistema verifica a privacidade da categoria.
    \item O sistema exibe mensagem: ``Esta categoria não está disponível.''
    \item O sistema não exibe nenhum dado da categoria, nem mesmo o nome.
\end{enumerate}

\textbf{FA03:} Usuário acessado não é amigo confirmado
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 3 do FB01, o sistema identifica que não existe vínculo de amizade confirmado entre os usuários.
    \item O sistema exibe apenas as categorias com privacidade ``pública'' do perfil visitado.
    \item Categorias com privacidade ``somente amigos'' não são exibidas.
\end{enumerate}
\mbox{} \\ \hline

Requisitos Especiais & RNF03 - A privacidade das categorias deve ser respeitada rigorosamente em toda a navegação. RNF02 - O perfil deve ser carregado em até 3 segundos. RNF04 - A visualização deve ser responsiva em dispositivos móveis. \\ \hline

Condições Prévias & O usuário deve estar autenticado. O usuário visitado deve existir na plataforma. \\ \hline

Pós-Condições & O usuário visualiza o perfil e as categorias acessíveis do amigo. Nenhuma alteração é feita nos dados do amigo. O usuário pode iniciar o fluxo de seguir uma categoria a partir desta tela. \\ \hline

Pontos de Extensão & E01 - Seguir Categoria (estende o passo 8 do FB01, conforme RF-16 — permite ao usuário acompanhar uma categoria pública ou somente amigos a partir do perfil visitado). \\
