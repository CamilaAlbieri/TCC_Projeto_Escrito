\chapter{Elicitação de Requisitos e Análise}
\label{cap:05}
A engenharia de requisitos é uma etapa fundamental no processo de desenvolvimento de software, sendo responsável por definir o que o sistema deve fazer e sob quais restrições ele deve operar \cite{Valente2020}. 
Segundo \citeauthorandyear{Sommerville2011}, essa disciplina engloba as atividades de descoberta, análise, documentação e validação dos requisitos, constituindo a base sobre a qual todo o projeto será construído.
\citeauthorandyear{Pressman2016} complementam essa visão ao afirmar que a engenharia de requisitos envolve a coleta de informações sobre o sistema a ser desenvolvido, a análise do problema e a descrição, classificação e priorização dos requisitos identificados.

O processo de elicitação de requisitos, também chamado de levantamento ou descoberta de requisitos, consiste em reunir informações junto aos stakeholders para compreender suas necessidades e expectativas em relação ao sistema \cite{Sommerville2011}.
Diversas técnicas podem ser empregadas nessa etapa, como entrevistas, questionários, workshops, prototipação e análise de cenários de uso \cite{Valente2020}

Este capítulo apresenta os requisitos identificados para o sistema proposto, organizados em requisitos do usuário e requisitos do sistema, sendo estes últimos subdivididos em requisitos funcionais e não funcionais.

\section{Requisitos do Usuário}

Requisitos de usuário são declarações, em uma linguagem natural com diagramas, de quais serviços o sistema
deverá fornecer a seus usuários e as restrições com as quais este deve operar \cite{Sommerville2011}. Segundo \citeauthorandyear{Pressman2016}, destacam que um documento de requisitos de sistema precisa ser claro, consistente e completo, pois ele servirá de referência para desenvolvedores, gerentes de projeto e engenheiros de testes ao longo de todo o ciclo de vida do software.

No contexto deste projeto, os requisitos do usuário foram identificados com base nas necessidades de organização e personalização de coleções pessoais. O sistema proposto visa oferecer ao usuário uma plataforma onde ele possa criar, personalizar e gerenciar coleções de diversos tipos — como livros, filmes e séries —, com liberdade para definir layouts, campos personalizados e configurações visuais. Além disso, funcionalidades sociais, como adicionar amigos e acompanhar coleções de outros usuários, foram identificadas como necessidades relevantes para promover a interação e o engajamento na plataforma.

\section{Requisitos do Sistema}
\citeauthorandyear{Sommerville2011} diz que os requisitos do sistema são tradicionalmente classificados em requisitos funcionais, que descrevem as funcionalidades que o sistema deve oferecer, e requisitos não funcionais, que definem restrições de qualidade como desempenho, segurança e usabilidade. Eles constituem o núcleo da especificação do sistema, pois definem o escopo das funcionalidades a serem implementadas.

Essa classificação permite uma organização sistemática das especificações e facilita tanto o desenvolvimento quanto a validação do sistema. Assim, esta seção apresenta os requisitos identificados neste trabalho, organizados nas subseções a seguir.
\subsection{Requisitos Funcionais}
Segundo \citeauthorandyear{Sommerville2011}, requisitos funcionais descrevem as funções ou serviços que o sistema deve fornecer, ou seja, o que o sistema deve fazer.
Eles especificam as ações que o sistema deve ser capaz de realizar em resposta a entradas específicas ou em determinadas condições.

Os atores que interagem com o sistema são: \textbf{Usuário}, que representa a pessoa cadastrada na plataforma e responsável por criar, editar e gerenciar suas coleções e interações sociais;
 e o \textbf{Sistema}, que atua de forma autônoma em funcionalidades como exibição de fichas de itens, notificações e organização visual das coleções.
Os requisitos funcionais identificados para este sistema estão apresentados na Tabela~\ref{tab:reqFuncionais}.

RF-01 & Acesso ao Sistema &
\textbf{Ação:} Cadastrar

\textbf{Objeto:} Usuário

\textbf{Atributos:} nome (100 caracteres), email (150
caracteres), senha (mínimo 8 caracteres), foto de perfil
(JPEG/PNG, máx. 5 MB), descrição (500 caracteres).

\textbf{Exemplos:} Usuária preenche nome `Camila Albieri
Mattos', email `camilamattos.mila@gmail.com', senha
`Camila@2024' e conclui o cadastro com sucesso.

Usuário tenta cadastrar com o email
`camilamattos.mila@gmail.com', que já existe e recebe
mensagem de erro informando que o email já está em uso.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item Nome, email e senha são obrigatórios; foto de perfil
e descrição são opcionais.
\item O email deve estar em formato válido
(ex.: usuario@dominio.com).
\item Não podem ser registrados dois ou mais usuários com
o mesmo email.
\item A senha deve ter no mínimo 8 caracteres.
\item A senha deve ser armazenada de forma criptografada.
\end{enumerate}

RF-02 & Acesso ao Sistema &
\textbf{Ação:} Autenticar (login e logout)

\textbf{Objeto:} Usuário

\textbf{Atributos:} email (150 caracteres), senha (mínimo
8 caracteres), token de sessão (gerado automaticamente
pelo sistema).

\textbf{Exemplos:} Usuária informa
`camilamattos.mila@gmail.com' e `Camila@2024', o sistema
valida as credenciais e concede acesso à área restrita.

Usuário informa email não cadastrado e recebe a mensagem
`Credenciais de login inválidas'.

Usuário clica em `Sair' e tem sua sessão encerrada
imediatamente, sendo redirecionado para a tela de login.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item Email e senha são obrigatórios para realizar o login.
\item O sistema deve verificar se o email está cadastrado
e se a senha confere com o hash armazenado.
\item Não conferindo, o sistema deve exibir `Credenciais
de login inválidas' sem especificar qual campo está errado.
\item O token de sessão deve expirar após 30 minutos de
inatividade.
\item O logout deve encerrar imediatamente a sessão ativa
e invalidar o token.
\end{enumerate}

RF-03 & Conta de Usuário &
\textbf{Ação:} Editar

\textbf{Objeto:} Perfil do usuário

\textbf{Atributos:} nome de exibição (100 caracteres),
email (150 caracteres), senha atual (para confirmação),
nova senha (mínimo 8 caracteres), foto de perfil
(JPEG/PNG, máx. 5 MB), descrição/bio (500 caracteres).

\textbf{Exemplos:} Usuário acessa `Editar Perfil`, altera
o nome de exibição para `Cami Mattos`, adiciona bio
`Leitora e colecionadora de histórias' e salva as
alterações.

Usuário tenta alterar a senha informando a senha atual
incorreta e recebe mensagem `Senha atual inválida`.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item O nome de exibição deve ter entre 3 e 100 caracteres
e é obrigatório.
\item Para alterar a senha, o usuário deve confirmar a
senha atual antes de definir a nova.
\item A foto de perfil deve estar em formato JPEG ou PNG
com tamanho máximo de 5 MB.
\item A descrição/bio é opcional e pode ser deixada em
branco.
\item Alterações só têm efeito após o usuário salvar
explicitamente.
\end{enumerate}

RF-04 & Gestão de Colecoes &
\textbf{Ação:} Cadastrar, editar e excluir

\textbf{Objeto:} Coleção personalizada

\textbf{Atributos:} nome (100 caracteres), tipo/categoria
(livros, filmes, series, jogos, musicas, personalizado),
ícone (emoji Unicode ou imagem JPEG/PNG, máx. 2 MB),
descrição (300 caracteres), layout associado (referência
a um layout existente do usuário), data de criação
(gerada automaticamente).

\textbf{Exemplos:} Usuária Camila cria a coleção `Meus
Livros' do tipo `Livros', com ícone personalizado,
descrição `Todos os livros que já li' e layout
`Card de Livro'.

Camila edita o nome para `Livros Lidos 2024' e troca o
layout associado.

Camila exclui a coleção `Filmes Antigos' e confirma a
exclusão permanente no diálogo de confirmação.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item O nome da coleção é obrigatório; ícone, descrição e
layout associado são opcionais.
\item Não podem existir duas coleções com o mesmo nome
para o mesmo usuário.
\item O tipo da coleção determina os campos padrão
disponíveis para os itens.
\item O layout associado pode ser alterado ou removido a
qualquer momento sem modificar os dados dos itens já
cadastrados.
\item A exclusão deve exibir diálogo de confirmação
alertando que todos os itens e subcoleções associadas
serão removidos permanentemente.
\item A data de criação é gerada automaticamente pelo
sistema e não pode ser editada.
\end{enumerate}

RF-05 & Itens de Colecao &
\textbf{Ação:} Cadastrar, editar e excluir

\textbf{Objeto:} Item dentro de uma coleção

\textbf{Atributos:} nome (200 caracteres), widgets
preenchíveis herdados do template da coleção (Imagem,
Texto, Classificação, Lista, Data, GIF, Formas, Elementos
Gráficos, Input Field, Icon), widgets adicionados
individualmente ao item (override), data de criação
(gerada automaticamente).

\textbf{Exemplos:} Camila cria o item `Duna' na coleção
`Livros' que usa o template `Card de Livro'; o item abre
com os widgets já estruturados e Camila adiciona as informações 
de cada widget do Template associado: Imagem para a capa, Input
Field para o autor `Frank Herbert', Data de inicio
`01/01/2024' e fim `20/01/2024', Classificação com 5
estrelas, Lista de gêneros `Ficção Cientifica, Aventura'
e Texto para a nota `Obra-prima do gênero'.

Camila também decide adicionar individualmente um widget de GIF
e um Input Field extra `Personagem Favorito: Paul
Atreides', sem afetar o template nem os demais itens.

Posteriormente edita a classificação de 5 para 4 estrelas
e, por fim, exclui o item `Duna -- Rascunho' confirmando
no diálogo de confirmação.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item O nome do item é obrigatório; todos os demais campos
são opcionais.
\item Ao ser criado, o item herda automaticamente a
estrutura de widgets do template associado à coleção como
ponto de partida.
\item O usuário pode adicionar, remover ou reposicionar
widgets individualmente no item sem afetar o template nem
os demais itens.
\item Não podem existir dois itens com o mesmo nome dentro
da mesma colecao.
\item Imagens enviadas devem estar em formato JPEG ou PNG
com tamanho máximo de 5 MB por arquivo.
\item A exclusao deve exibir diálogo de confirmação
informando que a ação é irreversível.
\item A data de criação é gerada automaticamente e não
pode ser editada pelo usuário.
\end{enumerate}

RF-06 & Ficha de Item &
\textbf{Ação:} Exibir em modo leitura

\textbf{Objeto:} Ficha individual de item

\textbf{Atributos:} widgets preenchidos do item (conforme
layout individual), widgets vazios (exibidos com indicação
visual), data de criação do item, modo de acesso (dono --
com opções de editar e excluir; visitante -- somente
leitura).

\textbf{Exemplos:} Camila acessa a ficha do item `Duna'
e visualiza todos os widgets preenchidos com os botoes
de editar e excluir disponíveis.

Um amigo visita a coleção pública `Livros' de Camila,
abre a ficha do item `Duna' e visualiza os mesmos
widgets, porém sem nenhuma opção de edição disponível.

Widget não preenchidos não são exibidos para visitantes.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item A ficha exibe todos os widgets do layout individual
do item, preenchidos ou não.
\item Widgets não preenchidos devem ser ocultados para visitantes, 
mas exibidos para o dono do item com indicação visual de que estão vazios.
\item Para o dono do item, a ficha deve oferecer acesso
direto às ações de editar e excluir.
\item Para visitantes, a ficha é estritamente somente
leitura, sem nenhuma opção de edição visível.
\item A ficha deve respeitar o tema visual configurado
pelo dono da coleção.
\end{enumerate}

\textbf{Objeto:} Layout personalizado (template)

\textbf{Atributos:} nome do layout (100 caracteres),
widgets disponíveis (Imagem, Texto, Classificação, Lista,
Data, GIF, Formas, Elementos Gráficos, Input Field, Icon,
Templates), posição e tamanho de cada widget na área de
edição.

\textbf{Exemplos:} Camila cria o layout `Card de Livro'

Classificação de 1 a 5 estrelas, dois campos de Data

Camila reposiciona o widget de Classificação via
drag-and-drop e visualiza o resultado em tempo real na

Camila exclui o layout `Card Antigo' que não estava

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]

usuário.
\item Pelo menos um widget deve ser adicionado para que
o layout possa ser salvo.
\item Widgets podem ser reposicionados e redimensionados
via arrastar e soltar (drag-and-drop).
\item Alterações devem ser refletidas em tempo real na
prévia do editor, sem recarregar a página.
\item O usuário pode excluir um layout somente se ele não
estiver associado a nenhuma coleção ativa.
\end{enumerate}

RF-08 & Editor de Layout &
\textbf{Ação:} Associar

\textbf{Objeto:} Layout (template) a uma coleção

\textbf{Atributos:} coleção de destino (existente e
pertencente ao usuário), layout selecionado (existente e
pertencente ao usuário).

\textbf{Exemplos:} Camila associa o layout `Card de Livro'
à coleção `Minha Biblioteca'; ao cadastrar novo item, os
widgets do layout são exibidos automaticamente como base.
Camila troca o layout da coleção `Series' de `Card
Simples' para `Card Completo'; os itens já existentes
não são alterados.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item Um layout só pode ser associado a uma coleção
existente e pertencente ao mesmo usuário.
\item Uma coleção pode ter apenas um layout padrão ativo
por vez.
\item A troca de layout não altera os dados nem os layouts
individuais dos itens já cadastrados.
\item O usuário pode remover a associação de layout de uma
coleção a qualquer momento.
\item Ao associar um layout, o sistema deve exibir prévia
de como os novos itens serão criados.
\end{enumerate}

RF-09 & Editor de Layout &
\textbf{Ação:} Modificar individualmente

\textbf{Objeto:} Layout herdado em um item específico

\textbf{Atributos:} widgets herdados do template da
coleção (base de partida), widgets adicionados pelo
usuário no item (override), widgets removidos pelo
usuário no item (override), widgets reposicionados ou
redimensionados no item (override).

\textbf{Exemplos:} Camila cria o item `Harry Potter e a
Pedra Filosofal' na coleção `Livros'; o item abre com o
template base; Camila adiciona widget extra de Input
Field `Data de Inicio de Leitura' apenas nesse item.

Camila remove o widget de GIF de um item específico pois
não se aplica, sem afetar o template nem os outros itens.

Camila restaura o layout original do template descartando
todas as modificações individuais do item.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item Todo item criado em uma coleção herda
automaticamente o template associado a ela como ponto
de partida.
\item O usuário pode adicionar, remover ou reposicionar
widgets no item sem afetar o template da coleção nem os
demais itens.
\item O template base deve ser exibido como referência
visual durante a edição individual do item.
\item O usuário pode restaurar o layout original do
template a qualquer momento, descartando todas as
modificações individuais do item.
\item As modificações individuais são exclusivas do item;
nenhuma alteração feita no item reflete no template.
\end{enumerate}

RF-10 & Subcolecoes &
\textbf{Ação:} Cadastrar, editar e excluir

\textbf{Objeto:} Subcoleção dentro de uma coleção
principal

\textbf{Atributos:} nome (100 caracteres), coleção pai
(referência obrigatória), ícone (emoji Unicode, opcional),
contagem de itens (calculada automaticamente).

\textbf{Exemplos:} Dentro da coleção `Livros', Camila
cria as subcoleções `Lidos', `Para Ler' e `Favoritos'.
Camila renomeia a subcoleção `Para Ler' para `Lista de
Desejos'.
Camila exclui a subcoleção `Abandonados'; os itens
retornam à coleção principal sem classificação.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item O nome da subcoleção é obrigatório.
\item Não podem existir duas subcoleções com o mesmo nome
dentro da mesma coleção pai.
\item Subcoleções não podem conter outras subcoleções
(apenas um nível de profundidade permitido).
\item A exclusao de uma subcolecao não exclui os itens;
eles permanecem na colecao principal sem classificação.
\item A contagem de itens de cada subcolecao é calculada
e exibida automaticamente pelo sistema.
\end{enumerate}

RF-11 & Subcolecoes &
\textbf{Ação:} Mover

\textbf{Objeto:} Item entre subcolecoes ou entre
subcolecao e colecao principal

\textbf{Atributos:} item de origem (nome, colecao e
subcolecao atual), destino (subcolecao existente ou
colecao principal).

\textbf{Exemplos:} Camila arrasta "A Metamorfose" da

origem e aparece no destino imediatamente.
Camila move "O Hobbit" da subcolecao "Fantasia" para a

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]

vez.
\item A movimentação deve ser concluída com no máximo
dois comandos (ex.: arrastar e soltar, ou selecionar e
confirmar destino).
\item A movimentação não altera nenhum dado do item,
apenas sua classificação.
\item A operação deve ser reversível via ação de desfazer
(Ctrl+Z ou botão equivalente).
\item A contagem de itens das subcolecoes de origem e
destino deve ser atualizada imediatamente.
\end{enumerate}

RF-12 & Visualizacao &
\textbf{Ação:} Visualizar

\textbf{Objeto:} Itens de uma colecao

\textbf{Atributos:} modo de exibição (geral / por
subcolecao), criterios de ordenação (nome A--Z, nome
Z--A, data de criação, avaliação), criterios de filtro
(subcolecao, tags, campos personalizados).

\textbf{Exemplos:} Camila abre a colecao "Livros" em modo
"geral" e visualiza todos os 42 itens ordenados por data
de criação.
Camila filtra pela subcolecao "Lidos" e ordena por
avaliação decrescente, vendo apenas os livros já lidos
do melhor ao pior avaliado.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item O modo "geral" deve exibir todos os itens da
colecao, independentemente da subcolecao.
\item O filtro por subcolecao deve exibir somente os
itens pertencentes à subcolecao selecionada.
\item A ordenação padrão é por data de criação, do mais
recente ao mais antigo.
\item Itens sem subcolecao devem ser identificados
visualmente como "Sem classificação" no modo geral.
\item Os filtros e ordenações aplicados devem ser mantidos
durante a navegação na mesma colecao.
\end{enumerate}

RF-14 & Personalizacao Visual &
\textbf{Ação:} Alterar

\textbf{Atributos:} família de fonte (lista predefinida

12 px, máximo 24 px), espaco entre linhas (1.0 a 2.0),
espaco entre letras.

\textbf{Exemplos:} Camila altera a fonte para "Georgia",

previa reflete as mudanças antes da confirmação.

mensagem indicando que o valor mínimo é 12 px.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
\item As fontes disponíveis devem incluir ao menos cinco
opcoes tipográficas distintas
(ex.: serif, sans-serif, monospace).
\item O tamanho mínimo para a fonte base é 12 px e o
máximo é 24 px.
\item As alterações devem ser exibidas em área de previa
antes de o usuário confirmar a aplicação.
\item As configurações de tipografia devem ser aplicadas
globalmente e persistidas entre sessões.
\item O sistema deve bloquear combinações extremas que
comprometam a legibilidade mínima.
\end{enumerate}

\citeauthorandyear{Pressman2016}, dizem que esses requisitos especificam atributos como desempenho, usabilidade, segurança, confiabilidade e portabilidade, sendo fundamentais para garantir que o sistema atenda aos padrões de qualidade esperados.

\subsection{Restrições, Suposições e Dependências}
Esta seção apresenta os fatores que podem limitar decisões de desenvolvimento ou influenciar diretamente a implementação dos requisitos definidos.

\begin{itemize}
\item O sistema depende de conexão com a internet para sincronizar dados e exibir atualizações de amigos.
\item O desempenho do editor de layout está condicionado à capacidade do dispositivo do usuário.
\item A troca de dados entre usuários exige um servidor ativo e funcional.

\section{Casos de Uso}
Conforme \citeauthorandyear{Valente2020}, um caso de uso descreve a sequência de interações realizadas por um ator com um sistema para atingir um objetivo específico, sendo esse ator, em geral, uma entidade externa, como um usuário humano ou outro sistema. 
Logo, um caso de uso é uma descrição de um cenário específico de interação entre um ator e o sistema, detalhando as ações realizadas e os resultados esperados. Ele é utilizado para capturar os requisitos funcionais do sistema, fornecendo uma visão clara e estruturada das funcionalidades que o sistema deve oferecer.

Descrição Resumida & Este caso de uso permite que o usuário envie solicitações de amizade para outros usuários da plataforma, possibilitando a formação de uma rede social dentro do sistema. A solicitação fica pendente até que o destinatário a aceite ou recuse. \\ \hline

Fluxo Básico & \mbox{}
\textbf{FB01:} Envio de solicitação de amizade
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item O usuário acessa a área de busca de usuários ou área social.
	\item O usuário insere o código do usuário da pessoa que deseja adicionar.
	\item O sistema busca usuários correspondentes no banco de dados.
	\item O sistema exibe uma lista de resultados com nome, foto e nome de usuário.
	\item O usuário identifica a pessoa desejada e clica em "Adicionar Amigo".
	\item O sistema verifica se já existe uma relação de amizade ou solicitação pendente.
	\item O sistema cria uma solicitação de amizade pendente no banco de dados.
	\item O sistema envia notificação ao destinatário informando sobre a solicitação.
	\item O sistema exibe mensagem de sucesso: "Solicitação de amizade enviada."
	\item O sistema atualiza o botão para "Solicitação Pendente" no perfil do usuário destinatário.
\end{enumerate}
\mbox{} \\ \hline

Fluxos Alternativos & \mbox{}
\textbf{FA01:} Usuário não encontrado
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item No passo 3 do FB01, o sistema não encontra nenhum usuário correspondente à busca.
	\item O sistema exibe mensagem: "Nenhum usuário encontrado com este nome."
	\item O sistema retorna ao passo 2 do FB01.
\end{enumerate}

\textbf{FA02:} Já são amigos
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item No passo 6 do FB01, o sistema identifica que os usuários já são amigos.
	\item O sistema exibe mensagem: "Vocês já são amigos."
	\item O sistema oferece opção de visualizar o perfil do amigo.
	\item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA03:} Solicitação já existe
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item No passo 6 do FB01, o sistema identifica que já existe uma solicitação pendente.
	\item O sistema exibe mensagem: "Você já enviou uma solicitação de amizade para este usuário."
	\item O sistema oferece opção de cancelar a solicitação pendente.
	\item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA04:} Solicitação recebida do mesmo usuário
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item No passo 6 do FB01, o sistema identifica que existe uma solicitação pendente enviada pelo usuário que está sendo adicionado.
	\item O sistema exibe mensagem: "Este usuário já enviou uma solicitação de amizade para você."
	\item O sistema oferece opção de aceitar a solicitação existente.
	\item Se o usuário aceitar, o sistema aciona o caso de uso "Gerenciar Solicitações de Amizade".
\end{enumerate}

\textbf{FA05:} Usuário bloqueado
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
	\item No passo 6 do FB01, o sistema identifica que um dos usuários bloqueou o outro.
	\item O sistema exibe mensagem genérica: "Não foi possível enviar a solicitação."
	\item O caso de uso é encerrado.
\end{enumerate}
\mbox{} \\ \hline

Condições Prévias & O usuário deve estar autenticado no sistema. O usuário destinatário deve existir e ter um perfil ativo. \\ \hline

Pós-Condições & Uma solicitação de amizade é criada com status "pendente". O destinatário recebe notificação da solicitação. A solicitação aparece na lista de pendentes de ambos os usuários. O botão no perfil do destinatário muda para "Solicitação Pendente". \\ \hline
