\chapter{Elicitação de Requisitos e Análise}
\label{cap:05}
A engenharia de requisitos é uma etapa fundamental no processo de desenvolvimento de software, sendo responsável por definir o que o sistema deve fazer 
e sob quais restrições ele deve operar \cite{Valente2020}. 
Segundo \cite{Sommerville2011}, essa disciplina engloba as atividades de descoberta, análise, documentação e validação dos requisitos, constituindo a base 
sobre a qual todo o projeto será construído.
\cite{pressman2016} complementam essa visão ao afirmar que a engenharia de requisitos envolve a coleta de informações sobre o sistema a ser desenvolvido, 
a análise do problema e a descrição, classificação e priorização dos requisitos identificados.

O processo de elicitação de requisitos, também chamado de levantamento ou descoberta de requisitos, consiste em reunir informações junto aos stakeholders 
para compreender suas necessidades e expectativas em relação ao sistema \cite{Sommerville2011}.
Diversas técnicas podem ser empregadas nessa etapa, como entrevistas, questionários, workshops, prototipação e análise de cenários de uso \cite{Valente2020}

Este capítulo apresenta os requisitos identificados para o sistema proposto, organizados em requisitos do usuário e requisitos do sistema, sendo estes últimos subdivididos em requisitos funcionais e não funcionais.


\section{Requisitos do Usuário}

Requisitos de usuário são declarações, em linguagem natural com diagramas, dos serviços que o sistema deverá fornecer aos seus usuários e das restrições 
com as quais ele deve operar \cite{Sommerville2011}. \citeauthorandyear{pressman2016} destacam que um documento de requisitos de sistema precisa ser claro, 
consistente e completo, pois servirá de referência para desenvolvedores, gerentes de projeto e engenheiros de testes ao longo de todo o ciclo de vida do software.

Antes de apresentar os requisitos propriamente ditos, é importante compreender três conceitos centrais que estruturam a forma como os dados do sistema se 
relacionam: \textbf{Elemento}, \textbf{Layout} e \textbf{Item}. Para facilitar o entendimento, vale partir de uma ferramenta já conhecida: 
editores visuais como o \textit{Canva}. Neles, o usuário monta uma tela arrastando elementos --- caixas de texto, imagens, formas, ícones --- e ajustando livremente 
a posição e o tamanho de cada um. A plataforma proposta segue essa mesma ideia, mas com um diferencial: a tela montada não é uma arte isolada, e sim um 
\textbf{modelo} que pode ser reaproveitado por dezenas ou centenas de itens de uma coleção, cada um com seus próprios dados.

A partir dessa analogia, os conceitos podem ser entendidos assim: o \textbf{Elemento} é cada peça que o usuário arrasta para a tela 
(uma caixa de texto, uma imagem, uma classificação por estrelas); o \textbf{TipoElemento} é o conjunto fixo de tipos de elemento disponíveis no editor; o \textbf{Layout} é a tela montada, isto é, o conjunto de elementos (\textit{Elementos})
 organizados visualmente, funcionando como um \textit{modelo} reutilizável; e o \textbf{Item} é uma unidade concreta do acervo do usuário que adota esse modelo
  (por exemplo, o livro ``Duna''). O conteúdo exibido pode estar diretamente nos elementos textuais, como em ``Autor:'' ou ``Autor: Frank Herbert'', e o usuário pode separar rótulos e valores criando elementos independentes quando desejar.

Uma analogia complementar, mais próxima da estrutura de dados, é a de um \textbf{formulário visual reutilizável}. O \textit{Layout} funciona como 
um formulário em branco, definindo quais elementos existem, sua posição e seu tamanho; os elementos são os campos ou objetos visuais em si; e o \textit{Item} é a unidade que utiliza esse modelo dentro de uma coleção. Quando necessário, um item pode receber uma versão visual própria por meio de \textit{override}, sem alterar o layout da coleção nem os demais itens.

Em termos práticos, considere um exemplo concreto. Suponha que o usuário crie um Layout chamado \textit{``Card de Livro''} contendo quatro elementos: 
um de \textit{Imagem} para a capa, um \textit{campo de texto} para o autor, um elemento de \textit{Classificação} de um a cinco estrelas e uma área de \textit{Texto} 
para notas pessoais. Cada elemento possui posição e tamanho próprios dentro da área de edição do layout. Ao cadastrar o item \textit{``Duna''}, o sistema gera 
os elementos visuais correspondentes para preenchimento e leitura: para o elemento \textit{Imagem}, a capa; para o \textit{campo de texto}, 
o autor \textit{``Frank Herbert''}; para o elemento \textit{Classificação}, o valor \textit{5}; e para o elemento \textit{Texto}, a nota 
\textit{``Obra-prima do gênero''}. Desse modo, o Layout e seus elementos permanecem reutilizáveis por diferentes itens da coleção, enquanto cada 
 item preserva sua própria ficha visual.

Essa separação traz três benefícios diretos para o projeto: 

(i) permite que o usuário reutilize o mesmo layout para múltiplos itens sem duplicação de estrutura; 

(ii) viabiliza que cada item preserve valores distintos, respeitando a individualidade de cada obra cadastrada; e 

(iii) permite modificações individuais em um item específico --- por exemplo, adicionar um elemento extra apenas a um único livro --- sem afetar o layout original nem os demais itens (RF-17).

Cabe esclarecer dois pontos sobre os tipos de elemento. Em primeiro lugar, o conjunto de tipos é \textbf{fixo} e definido por uma enumeração (TipoElemento), 
e não um cadastro gerido em tempo de execução. Essa decisão segue o modelo de editores visuais consolidados, como o Canva, nos quais os \textit{tipos} de elemento 
(texto, imagem, formas, entre outros) fazem parte das capacidades nativas da ferramenta, enquanto o que o usuário cria livremente são \textit{instâncias} desses tipos 
--- isto é, quantos elementos quiser, arrastando, redimensionando e posicionando-os na tela. A eventual inclusão de um tipo inteiramente novo (por exemplo, vídeo incorporado) 
caracteriza uma evolução do próprio editor, e não um dado a ser cadastrado pelo usuário final.

Em segundo lugar, é importante distinguir os tipos \textit{texto fixo} e \textit{campo de texto}, que visualmente se assemelham, mas têm naturezas distintas. 
O \textbf{texto fixo} é um rótulo definido uma única vez no layout e idêntico em todos os itens que o utilizam (por exemplo, o rótulo ``Autor:''). 
Já o \textbf{campo de texto} é um espaço cujo conteúdo varia de item para item e é preenchido pelo usuário ao editar cada item (por exemplo, o valor ``Rick Riordan''). 
Em termos de modelo, o texto fixo reside no Layout (compartilhado por todos os itens), ao passo que o valor de um campo de texto varia conforme a ficha do item. 
É essa separação que permite reaproveitar um mesmo layout em centenas de itens, cada qual com seus próprios valores.

\subsection{Organização em Pacotes}
\label{subsec:pacotes_dominio}

Devido à quantidade de classes conceituais envolvidas, o modelo de domínio foi organizado em sete pacotes, de modo a agrupar entidades que compartilham propósito semântico e
reduzir a complexidade visual do diagrama. Essa segmentação segue a recomendação de \cite{Larman2007}, segundo o qual o agrupamento de classes em pacotes facilita a leitura do modelo, 
evidencia suas fronteiras conceituais e favorece o raciocínio modular sobre o sistema. Os pacotes adotados neste trabalho são:

\begin{itemize}[nosep,leftmargin=1.5em,topsep=4pt,partopsep=0pt,
               parsep=2pt,itemsep=4pt]

  \item \textbf{Usuário} --- concentra a entidade central da plataforma,
  responsável pelos dados de identificação e pelo vínculo com todas as demais
  entidades do sistema. Foi isolada em um pacote próprio por atuar como ponto
  de referência para os demais agrupamentos.

  \item \textbf{Coleções} --- reúne as entidades que compõem a estrutura de
  organização do acervo em três níveis hierárquicos: Categoria, Coleção e
  Item. Inclui também a enumeração de
  privacidade. Representa o núcleo de domínio da aplicação, pois é nele que
  o usuário efetivamente cadastra e organiza seu conteúdo.

  \item \textbf{Editor de Layout} --- agrupa as entidades responsáveis pela
  personalização visual das fichas de itens, incluindo Layout, Elemento e a
  enumeração TipoElemento, que define o conjunto fixo de tipos de elemento
  disponíveis no editor (texto fixo, campo de texto, imagem, gif, forma, ícone,
  classificação, data e lista). É este pacote que sustenta o diferencial de
  customização da plataforma.

  \item \textbf{Interação Social} --- concentra as entidades ligadas aos
  vínculos entre usuários, como as solicitações de amizade (Amizade e
  StatusAmizade) e o acompanhamento de coleções de outros usuários
  (Seguir Coleção).

  \item \textbf{Notificações} --- reúne as entidades responsáveis pelo
  registro e pela exibição de eventos relevantes ao usuário: a própria
  entidade Notificação, a enumeração TipoNotificacao, a entidade
  AtualizaçãoEvento e a enumeração TipoEvento. A separação deste pacote
  em relação ao de Interação Social reflete a distinção entre o vínculo
  social em si e o mecanismo de comunicação dessas ocorrências ao usuário,
  além de isolar a lógica de geração e exibição de notificações para
  facilitar futuras extensões do sistema.

  \item \textbf{Aparência} --- reúne as entidades que definem a configuração
  visual global da interface, como paletas de cores, tipografia e seleção de
  tema claro ou escuro.

  \item \textbf{Sistema} --- reúne as entidades de apoio à operação da
  plataforma, que não pertencem ao domínio do acervo nem às interações entre
  usuários: a sessão de usuário, que permite revogar o acesso no momento do
  logout, e o token de redefinição de senha, de uso único e com prazo de
  validade. Foi isolado em pacote próprio por sustentar os requisitos de acesso
  sem participar das regras de negócio das coleções.

\end{itemize}

Essa organização reflete a separação de responsabilidades identificada durante
a elicitação de requisitos: a entidade central do pacote \textit{Usuário}
sustenta o cadastro e o perfil (RF-01 e RF-05), enquanto as do pacote
\textit{Sistema} viabilizam a autenticação, a alteração e a recuperação de
senha (RF-02 a RF-04); as classes do pacote \textit{Coleções} sustentam os
requisitos funcionais de gestão de conteúdo (RF-06 a RF-13); as do pacote
\textit{Editor de Layout} suportam os requisitos de personalização estrutural
(RF-14 a RF-17); as do pacote \textit{Aparência} viabilizam a configuração
visual global criada no cadastro e ajustável pelo usuário (RF-18 e RF-19); as
do pacote \textit{Interação Social} dão suporte às funcionalidades de rede
entre usuários (RF-20 a RF-23); e as do pacote \textit{Notificações} sustentam
o mecanismo de comunicação de eventos do sistema ao usuário (RF-24).

Cabe observar que os grupos de requisitos e os pacotes conceituais são recortes
distintos e não coincidem termo a termo. O grupo \textit{Acesso ao Sistema}
(RF-01 a RF-05), por exemplo, distribui-se entre dois pacotes: os dados de
identificação do usuário residem em \textit{Usuário}, ao passo que as
estruturas que sustentam sessão e redefinição de senha residem em
\textit{Sistema}. O agrupamento em pacotes obedece à afinidade conceitual entre
as classes, e não à organização adotada na especificação dos requisitos.

O modelo de domínio resultante é apresentado na Seção~\ref{sec:modelo_dominio},
ao final deste capítulo, depois de detalhados os requisitos e os casos de uso
que o originaram.


\section{Requisitos do Sistema}

\citeauthorandyear{Sommerville2011} afirma que os requisitos do sistema são tradicionalmente classificados em requisitos \textbf{funcionais}, 
que descrevem as funcionalidades que o sistema deve oferecer, e requisitos \textbf{não funcionais}, que definem restrições de qualidade como desempenho, 
segurança e usabilidade. Eles constituem o núcleo da especificação do sistema, pois delimitam o escopo das funcionalidades a serem implementadas, 
e sua classificação permite uma organização sistemática das especificações, facilitando tanto o desenvolvimento quanto a validação do sistema.

Assim, esta seção apresenta os requisitos identificados neste trabalho, organizados nas subseções a seguir.


\subsection{Requisitos Funcionais}

Segundo \citeauthorandyear{Sommerville2011}, requisitos funcionais descrevem as funções ou serviços que o sistema deve fornecer, ou seja, o que o sistema deve fazer. 
Eles especificam as ações que o sistema deve ser capaz de executar em resposta a entradas específicas ou em determinadas condições.

Os atores que interagem com o sistema são: \textbf{Usuário}, que representa a pessoa cadastrada na plataforma e responsável por criar, editar e gerenciar suas categorias, 
coleções, itens e interações sociais; e o \textbf{Sistema}, que atua de forma autônoma em funcionalidades como exibição de fichas de itens, envio de notificações, 
atualização do feed em tempo real e organização visual dos dados.

Para padronizar a especificação dos requisitos, adotou-se o verbo \textbf{gerenciar} como forma genérica de representar operações do tipo CRUD (cadastrar, editar e excluir), 
sempre que aplicável. Essa padronização reduz a repetição textual e torna a descrição dos requisitos mais objetiva.

Os requisitos funcionais estão organizados em seis grupos, apresentados de forma sequencial e seguindo uma ordem lógica de dependência entre funcionalidades, 
alinhada à jornada natural do usuário no sistema: iniciam pelo \textbf{Acesso ao Sistema} (cadastro, autenticação, recuperação e alteração de senha e gerenciamento de perfil); prosseguem com a \textbf{Coleção}, núcleo do sistema (categorias, coleções, privacidade, itens, suas fichas e formas de visualização); avançam para o \textbf{Editor de Layout} (criação de layouts, associação a coleções, compartilhamento entre usuários e personalização individual); seguem para a \textbf{Aparência}, camada de personalização visual que se aplica sobre o conteúdo já organizado (tema, cores e tipografia); contemplam a \textbf{Interação Social} (amizade, acompanhamento de coleções e visualização de perfis); e culminam na \textbf{Notificação}, mecanismo de comunicação de eventos ao usuário.
Os quadros~\ref{quad:descricao_campos} a~\ref{quad:atores} apresentam a definição dos campos e das classificações utilizadas na especificação, e os requisitos funcionais 
identificados para este sistema estão apresentados nos Quadros~\ref{quad:rf01} a~\ref{quad:rf24}.

  \item O sistema deve verificar se o email está cadastrado e se a senha confere com o hash armazenado.

  \item O token de sessão deve ter prazo de validade definido, expirando automaticamente ao final desse prazo.
  \item A validade da sessão deve ser verificada pelo sistema a cada requisição autenticada, de modo que uma sessão revogada deixe de conceder acesso imediatamente, mesmo que o token ainda não tenha expirado.
  \item O logout deve revogar imediatamente a sessão ativa, tornando o token inutilizável a partir desse momento.
\end{enumerate} \\ \hline

\textbf{Atributos:} tipo de evento (adição, edição ou remoção de item em coleção seguida), item afetado ou registro mínimo do item quando ele já tiver sido removido, coleção seguida, categoria pai, usuário autor da ação, data e hora do evento e descrição textual auxiliar.

\textbf{Exemplos:} Feed de Camila exibe `João adicionou Oppenheimer na coleção Filmes Assistidos (categoria Filmes) -- há 2 horas'.
Feed exibe `Ana avaliou o item Breaking Bad na coleção Séries Concluídas -- há 5 minutos'.

\textbf{Restrições:}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=2pt,partopsep=0pt,parsep=0pt,itemsep=1pt]
  \item O feed deve exibir apenas eventos de coleções que o usuário segue ativamente (RF-21).
  \item Os eventos devem ser ordenados cronologicamente, do mais recente ao mais antigo.
  \item O feed deve ser atualizado automaticamente em tempo real, sem necessidade de recarregar a página.
  \item Se a privacidade de uma coleção seguida for alterada para `privada', os eventos anteriores dessa coleção não devem mais ser exibidos, e o acompanhamento é encerrado automaticamente (RF-21).
  \item Eventos de criação ou exclusão de coleção em si não são exibidos no feed; a descoberta de novas coleções ocorre por meio da visita a perfis de usuários (RF-23).

  \item O registro de evento deve usar campos estruturados (coleção, item quando aplicável e usuário autor) como fonte principal dos dados; a descrição textual é apenas informação auxiliar.
  \item Eventos de remoção de item devem preservar um registro mínimo do item afetado, de modo que o histórico continue compreensível após a exclusão do item.

\subsection{Requisitos Não-Funcionais}
Segundo \citeauthorandyear{Sommerville2011}, os requisitos não funcionais são requisitos que não estão diretamente relacionados com os serviços específicos oferecidos 
pelo sistema a seus usuários.
Logo, não dizem respeito diretamente às funcionalidades fornecidas pelo sistema, mas sim às suas propriedades e restrições de qualidade.
\citeauthorandyear{pressman2016}, dizem que esses requisitos especificam atributos como desempenho, usabilidade, segurança, confiabilidade e portabilidade, 
sendo fundamentais para garantir que o sistema atenda aos padrões de qualidade esperados.
Assim, esta seção apresenta os requisitos não-funcionais identificados neste trabalho, consolidados nos Quadros de ~\ref{quad:rnf01} a ~\ref{quad:rnf10}.

\subsection{Restrições, Suposições e Dependências}
Esta seção apresenta os fatores que podem limitar decisões de desenvolvimento ou influenciar diretamente a implementação dos requisitos definidos.

\begin{itemize}
\item O sistema depende de conexão com a internet para sincronizar dados e exibir atualizações de amigos.
\item O desempenho do editor de layout está condicionado à capacidade do dispositivo do usuário.
\item A troca de dados entre usuários exige um servidor ativo e funcional.
\item A expansão das funcionalidades sociais depende da adoção do sistema por múltiplos usuários.
\end{itemize}


\subsection{Requisitos Adiados}
Alguns requisitos foram identificados durante a elicitação, porém não serão implementados nesta primeira versão do sistema. Eles poderão ser considerados em iterações futuras.

\begin{itemize}
\item Implementação de chat privado entre usuários.
\item Recomendações automáticas baseadas nas coleções dos amigos.
\item Exportação de coleções em PDF ou outros formatos.
\item Mecanismos avançados de descoberta pública (explorar, ranking, tendências).
\end{itemize}

Além desses, dois requisitos especificados neste capítulo foram mantidos na especificação, por
integrarem o comportamento pretendido da plataforma, mas não chegaram a ser implementados na
etapa concluída até aqui:

\begin{itemize}
\item \textbf{Verificação de e-mail na alteração de endereço} (RF-05 e RF-24). O envio de
mensagens por e-mail já está disponível na plataforma, pois é utilizado na recuperação de senha
(RF-04); o fluxo específico de confirmação do novo endereço, contudo, ficou para uma etapa
posterior. Até lá, a alteração de e-mail tem efeito imediato.
\item \textbf{Atualização em tempo real do \textit{feed} e das notificações} (RF-22 e RF-24). As
notificações e os eventos de atualização são persistidos e disponibilizados por consulta à API,
mas a entrega por fluxo contínuo de eventos, que dispensaria o recarregamento da página,
permanece fora desta etapa.
\end{itemize}


\section{Casos de Uso}
Conforme \citeauthorandyear{Valente2020}, um caso de uso descreve a sequência de interações realizadas por um ator com um sistema para atingir um objetivo específico, 
sendo esse ator, em geral, uma entidade externa, como um usuário humano ou outro sistema. 
Logo, um caso de uso é uma descrição de um cenário específico de interação entre um ator e o sistema, detalhando as ações realizadas e os resultados esperados. 
Ele é utilizado para capturar os requisitos funcionais do sistema, fornecendo uma visão clara e estruturada das funcionalidades que o sistema deve oferecer.

\subsection{Especificação dos Casos de Uso}
Uma especificação de caso de uso fornece a descrição textual detalhada do comportamento do sistema a partir da perspectiva do usuário, permitindo compreender 
como as funcionalidades são executadas e quais resultados são esperados. As especificações apresentam os fluxos principais, fluxos alternativos, condições prévias 
e pós-condições associadas a cada interação.

Neste trabalho, foram elaboradas dezoito especificações textuais, cobrindo os casos de uso que possuem fluxo próprio e alternativas relevantes. Os demais casos de uso presentes nos diagramas não receberam especificação por representarem variações, detalhamentos ou funcionalidades já incluídas nos fluxos básicos aqui descritos --- é o caso, por exemplo, das operações de edição e exclusão, cujo fluxo espelha o de criação com a diferença do registro previamente selecionado. O modelo adotado para a especificação dos casos de uso é apresentado nos Quadros~\ref{tab:especFazerLogin}
a~\ref{tab:especVisualizarFeed}, adaptado da IBM.

Cabe destacar a estrutura hierárquica adotada pelo sistema, que organiza os dados em três níveis: \textbf{Categoria} (agrupador temático de alto nível, ex.: ``Livros''), 
\textbf{Coleção} (subdivisão de uma categoria onde os itens são efetivamente cadastrados e onde o layout é associado, ex.: ``Lidos'', ``Para Ler'') e \textbf{Item} 
unidade individual de conteúdo, ex.: o livro ``Duna''). Essa separação permite que o usuário organize seu acervo em duas camadas antes de cadastrar qualquer item, 
facilitando a categorização e a personalização por meio do layout definido em cada coleção.

\end{enumerate}

\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]

	\item O usuário seleciona um layout para duplicar.
	\item O sistema carrega a estrutura do layout selecionado no editor, pré-preenchendo o nome com o original acrescido de ``(cópia)''.
	\item O fluxo continua no passo 4 do FB01, com o usuário podendo renomear e ajustar a cópia livremente.

\end{enumerate}

\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]

	\item O sistema exibe mensagem de confirmação: ``Deseja descartar as alterações?''
	\item Se o usuário confirmar, o sistema descarta as informações e retorna à lista de layouts.
	\item Se o usuário cancelar, o sistema retorna ao editor mantendo as informações.
\end{enumerate}

Descrição Resumida & Este caso de uso permite que o usuário acompanhe em tempo real as atualizações das coleções que segue, visualizando eventos de adição, edição e remoção de itens realizados por seus proprietários, ordenados cronologicamente do mais recente ao mais antigo (RF-22). \\ \hline

Fluxo Básico & \mbox{}
\textbf{FB01:} Exibição do feed
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item O usuário acessa a área de feed de atualizações.
    \item O sistema identifica todas as coleções que o usuário segue ativamente (conforme RF-21).
    \item O sistema recupera os eventos de atualização associados a essas coleções (adição/edição/remoção de itens), ordenados do mais recente ao mais antigo.
    \item O sistema verifica a privacidade atual de cada coleção antes de exibir seus eventos (RF-08).
    \item O sistema exibe o feed com os eventos, contendo: nome do autor da ação, tipo de evento, nome do item afetado, nome da coleção, nome da categoria pai e data/hora relativa do evento.
    \item O feed é atualizado automaticamente em tempo real sem necessidade de recarregar a página.
    \item O usuário pode rolar o feed para carregar eventos mais antigos progressivamente (paginação).
\end{enumerate}
\mbox{} \\ \hline

Fluxos Alternativos & \mbox{}
\textbf{FA01:} Usuário não segue nenhuma coleção
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 2 do FB01, o sistema identifica que o usuário não segue nenhuma coleção.
    \item O sistema exibe mensagem: ``Seu feed está vazio. Siga coleções para acompanhar suas atualizações.''
    \item O sistema exibe atalho para a área de descoberta de perfis e coleções públicas.
\end{enumerate}

\textbf{FA02:} Coleção seguida alterada para privada
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 4 do FB01, o sistema identifica que uma coleção anteriormente seguida foi alterada para privada.
    \item O sistema não exibe os eventos dessa coleção, incluindo eventos anteriores à mudança de privacidade.
    \item O sistema encerra automaticamente o acompanhamento dessa coleção.
    \item Os demais eventos do feed continuam sendo exibidos normalmente.
\end{enumerate}

\textbf{FA03:} Erro ao carregar o feed
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item No passo 3 do FB01, o sistema encontra erro ao recuperar os eventos.
    \item O sistema exibe mensagem: ``Não foi possível carregar o feed. Tente novamente.''
    \item O sistema oferece botão para recarregar.
\end{enumerate}
\mbox{} \\ \hline

Requisitos Especiais & RNF-07 - O feed deve ser atualizado em tempo real sem recarregar a página. RNF-02 - O carregamento inicial do feed deve ocorrer em até 3 segundos. RNF-03 - Eventos de coleções privadas não devem ser exibidos em nenhuma circunstância. \\ \hline

Condições Prévias & O usuário deve estar autenticado. O usuário deve seguir ao menos uma coleção com privacidade pública ou somente amigos (RF-21). \\ \hline

Pós-Condições & O usuário visualiza os eventos recentes das coleções que segue. O feed permanece atualizado em tempo real durante a navegação. Coleções tornadas privadas são removidas do feed imediatamente, com seu acompanhamento encerrado. \\ \hline

Pontos de Extensão & Nenhum ponto de extensão identificado para este caso de uso. \\
\end{longtable}
