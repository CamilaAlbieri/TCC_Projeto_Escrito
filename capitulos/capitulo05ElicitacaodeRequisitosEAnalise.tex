\chapter{Elicitação de Requisitos e Análise}
\label{cap:05}
A engenharia de requisitos é uma etapa fundamental no processo de desenvolvimento de software, sendo responsável por definir o que o sistema deve fazer 
e sob quais restrições ele deve operar \cite{Valente2020}. 
Segundo \cite{Sommerville2011}, essa disciplina engloba as atividades de descoberta, análise, documentação e validação dos requisitos, constituindo a base 
sobre a qual todo o projeto será construído.
\cite{pressman2016} complementam essa visão ao afirmar que a engenharia de requisitos envolve a coleta de informações sobre o sistema a ser desenvolvido, 
a análise do problema e a descrição, classificação e priorização dos requisitos identificados.

O processo de elicitação de requisitos, também chamado de levantamento ou descoberta de requisitos, consiste em reunir informações junto aos stakeholders 
para compreender suas necessidades e expectativas em relação ao sistema \cite{Sommerville2011}.
Diversas técnicas podem ser empregadas nessa etapa, como entrevistas, questionários, workshops, prototipação e análise de cenários de uso \cite{Valente2020}

Este capítulo apresenta os requisitos identificados para o sistema proposto, organizados em requisitos do usuário e requisitos do sistema, sendo estes últimos subdivididos em requisitos funcionais e não funcionais.


\section{Requisitos do Usuário}

Requisitos de usuário são declarações, em linguagem natural com diagramas, dos serviços que o sistema deverá fornecer aos seus usuários e das restrições 
com as quais ele deve operar \cite{Sommerville2011}. \citeauthorandyear{pressman2016} destacam que um documento de requisitos de sistema precisa ser claro, 
consistente e completo, pois servirá de referência para desenvolvedores, gerentes de projeto e engenheiros de testes ao longo de todo o ciclo de vida do software.

Antes de apresentar os requisitos propriamente ditos, é importante compreender os \textbf{quatro} conceitos centrais que estruturam a modelagem de dados da
plataforma proposta: \textbf{Elemento}, \textbf{TipoElemento}, \textbf{Layout} e \textbf{Item}. Para facilitar a compreensão do papel de cada um no sistema,
vale partir de uma analogia com ferramentas de edição visual consolidadas no mercado, como o \textit{Canva}. Nesses editores, o usuário monta uma tela de
forma livre, acrescentando componentes gráficos a partir de uma paleta, como caixas de texto, imagens e ícones, e ajustando em seguida a posição e o tamanho
de cada um. A plataforma proposta adota essa mesma dinâmica de montagem visual, mas com um diferencial fundamental: a tela montada pelo usuário não é uma
arte gráfica isolada, e sim um \textbf{modelo de dados reutilizável}, que pode ser compartilhado por dezenas ou centenas de itens de uma coleção,
preservando a individualidade das informações de cada um.

A partir dessa analogia, os quatro conceitos podem ser entendidos na mesma ordem. O \textbf{Elemento} é cada peça que o usuário acrescenta à tela, como uma
caixa de texto, uma imagem ou uma classificação por estrelas. É nele que residem tanto o conteúdo exibido quanto os atributos que determinam onde ele
aparece: posição, largura, altura e camada de sobreposição. O modo como ele aparece fica a cargo do \textbf{EstiloDeElemento}, conjunto de propriedades
visuais associado a cada Elemento, tratado adiante. O \textbf{TipoElemento} é a classificação desse Elemento dentro
do conjunto fixo de tipos que o editor oferece. Trata-se de uma enumeração, e não de uma entidade com atributos próprios, de modo que dois Elementos do
mesmo tipo, como ``Autor'' e ``Gênero'', ambos de texto, são registros distintos, cada um com suas próprias coordenadas. O \textbf{Layout} é a tela montada,
isto é, o conjunto de Elementos organizados visualmente, funcionando como um modelo reutilizável associado a uma coleção. E o \textbf{Item} é uma unidade
concreta do acervo do usuário, por exemplo o livro ``Duna'', que parte desse modelo e pode manter um layout próprio. O conteúdo exibido pode estar
diretamente nos Elementos textuais, como em ``Autor:'' ou ``Autor: Frank Herbert'', e o usuário pode separar rótulos e valores criando Elementos
independentes quando desejar.

Uma analogia complementar, mais próxima da estrutura de dados, é a de um \textbf{molde reutilizável}. O \textit{Layout} funciona como um molde já
desenhado, que define quais Elementos existem, sua posição e seu tamanho, mas não o que cada um exibe; os Elementos são as peças desenhadas nesse molde; e o
\textit{Item} é a unidade que parte dele dentro de uma coleção. Para receber valores próprios, o item ganha uma cópia do molde, o seu layout próprio,
que pode ser alterado sem afetar o layout da coleção nem os demais itens.

Em termos práticos, considere um exemplo concreto. Suponha que o usuário crie um Layout chamado \textit{``Card de Livro''} contendo quatro elementos: 
um de \textit{Imagem} para a capa, um de \textit{Texto} para o autor, um elemento de \textit{Classificação} de um a cinco estrelas e
outro de \textit{Texto} para notas pessoais. Cada elemento possui posição e tamanho próprios dentro da área de edição do layout. O usuário cadastra o item \textit{``Duna''} e, em seguida, abre
a sua ficha para preenchê-la. Nesse momento, o sistema copia para o item os elementos do layout, e é nessas cópias que ficam os valores do item:
para o elemento \textit{Imagem}, a capa; para o primeiro \textit{Texto}, o autor \textit{``Frank Herbert''}; para o elemento \textit{Classificação}, o valor \textit{5}; e para o elemento \textit{Texto}, a nota
\textit{``Obra-prima do gênero''}. Desse modo, o Layout e seus elementos permanecem reutilizáveis por diferentes itens da coleção, enquanto cada
 item preserva sua própria ficha visual.

Essa separação traz três benefícios diretos para o projeto: 

(i) permite que o usuário reutilize o mesmo layout para múltiplos itens sem duplicação de estrutura; 

(ii) viabiliza que cada item preserve valores distintos, respeitando a individualidade de cada obra cadastrada; e 

(iii) permite modificações individuais em um item específico, como adicionar um Elemento extra apenas a um único livro, sem afetar o layout original nem os demais itens (RF-17).

Cabe esclarecer dois pontos antes de apresentar os requisitos. Em primeiro lugar, o conjunto de tipos de elemento é \textbf{fixo} e definido por uma enumeração (TipoElemento),
e não um cadastro gerido em tempo de execução. Essa decisão segue o modelo de editores visuais consolidados, como o Canva, nos quais os \textit{tipos} de elemento 
(texto, imagem, formas, entre outros) fazem parte das capacidades nativas da ferramenta, enquanto o que o usuário cria livremente são \textit{instâncias} desses tipos:
quantos elementos quiser, acrescentando-os pela paleta e depois posicionando-os e redimensionando-os na tela. A eventual inclusão de um tipo inteiramente novo (por exemplo, vídeo incorporado)
caracteriza uma evolução do próprio editor, e não um dado a ser cadastrado pelo usuário final.

Em segundo lugar, cabe registrar onde reside o conteúdo de cada item, pois é disso que depende a relação entre o Layout e o Item. O conteúdo não é guardado
em uma entidade à parte: fica no próprio Elemento, ao lado da posição, do tamanho e das propriedades visuais. O Layout associado a uma coleção define apenas
quais Elementos existem e como se organizam, sem guardar o que qualquer item exibe. A individualização ocorre em outro nível: na primeira vez em que a
ficha do item é aberta para edição, o Item recebe um \textbf{layout próprio}, copiado do layout da coleção quando ela possui um, ou vazio quando não
possui (RF-17). A interface abre essa ficha logo depois do cadastro, de modo que, no uso normal, todo item preenchido tem seus próprios Elementos, nos
quais conteúdo, posição e estilo permanecem indissociáveis. Chama-se \textbf{layout efetivo} de um item o seu layout próprio, quando existe, ou, na falta
dele, o layout da coleção; esse segundo caso corresponde ao item cuja ficha ainda não foi aberta, que exibe o layout da coleção tal como ele está.

\subsection{Organização em Pacotes}
\label{subsec:pacotes_dominio}

Devido à quantidade de classes conceituais envolvidas, o modelo de domínio foi organizado em sete pacotes, de modo a agrupar entidades que compartilham propósito semântico e
reduzir a complexidade visual do diagrama. Essa segmentação segue a recomendação de \cite{Larman2007}, segundo o qual o agrupamento de classes em pacotes facilita a leitura do modelo, 
evidencia suas fronteiras conceituais e favorece o raciocínio modular sobre o sistema. Os pacotes adotados neste trabalho são:

\begin{itemize}[nosep,leftmargin=1.5em,topsep=4pt,partopsep=0pt,
               parsep=2pt,itemsep=4pt]

  \item \textbf{Usuário:} concentra a entidade central da plataforma,
  responsável pelos dados de identificação e pelo vínculo com todas as demais
  entidades do sistema. Foi isolada em um pacote próprio por atuar como ponto
  de referência para os demais agrupamentos.

  \item \textbf{Coleções:} reúne as entidades que compõem a estrutura de
  organização do acervo em três níveis hierárquicos: Categoria, Coleção e
  Item. Inclui também a enumeração de
  privacidade. Representa o núcleo de domínio da aplicação, pois é nele que
  o usuário efetivamente cadastra e organiza seu conteúdo.

  \item \textbf{Editor de Layout:} agrupa as entidades responsáveis pela
  personalização visual das fichas de itens, incluindo Layout, Elemento, o
  EstiloDeElemento, que reúne as propriedades visuais de cada Elemento, e a
  enumeração TipoElemento, que define o conjunto fixo de tipos de elemento
  disponíveis no editor (texto, imagem, forma, ícone, classificação e
  data). É este pacote que sustenta o diferencial de
  customização da plataforma.

  \item \textbf{Interação Social:} concentra as entidades ligadas aos
  vínculos entre usuários, como as solicitações de amizade (Amizade e
  StatusAmizade) e o acompanhamento de coleções de outros usuários
  (Seguir Coleção).

  \item \textbf{Notificações:} reúne as entidades responsáveis pelo
  registro e pela exibição de eventos relevantes ao usuário: a própria
  entidade Notificação, a enumeração TipoNotificacao, a entidade
  AtualizaçãoEvento e a enumeração TipoEvento. A separação deste pacote
  em relação ao de Interação Social reflete a distinção entre o vínculo
  social em si e o mecanismo de comunicação dessas ocorrências ao usuário,
  além de isolar a lógica de geração e exibição de notificações para
  facilitar futuras extensões do sistema.

  \item \textbf{Aparência:} reúne as entidades que definem a configuração
  visual global da interface: a biblioteca de paletas do usuário, cada uma
  com suas cores, sua tipografia e seu estilo claro ou escuro.

  \item \textbf{Sistema:} reúne as entidades de apoio à operação da
  plataforma, que não pertencem ao domínio do acervo nem às interações entre
  usuários: a sessão de usuário, que permite revogar o acesso no momento do
  logout, o token de redefinição de senha, de uso único e com prazo de
  validade, e o código de confirmação do e-mail, exigido antes do primeiro
  acesso. Foi isolado em pacote próprio por sustentar os requisitos de acesso
  sem participar das regras de negócio das coleções.

\end{itemize}

Essa organização reflete a separação de responsabilidades identificada durante
a elicitação de requisitos: a entidade central do pacote \textit{Usuário}
sustenta o cadastro e o perfil (RF-01 e RF-05), enquanto as do pacote
\textit{Sistema} viabilizam a confirmação do e-mail no cadastro (RF-01), a
autenticação, a alteração e a recuperação de senha (RF-02 a RF-04); as classes do pacote \textit{Coleções} sustentam os
requisitos funcionais de gestão de conteúdo (RF-06 a RF-13); as do pacote
\textit{Editor de Layout} suportam os requisitos de personalização estrutural
(RF-14 a RF-17); as do pacote \textit{Aparência} viabilizam a biblioteca de
paletas oferecida no cadastro e gerenciada pelo usuário (RF-18 e RF-19); as
do pacote \textit{Interação Social} dão suporte às funcionalidades de rede
entre usuários (RF-20 a RF-23); e as do pacote \textit{Notificações} sustentam
o mecanismo de comunicação de eventos do sistema ao usuário (RF-24).

Cabe observar que os grupos de requisitos e os pacotes conceituais são recortes
distintos e não coincidem termo a termo. O grupo \textit{Acesso ao Sistema}
(RF-01 a RF-05), por exemplo, distribui-se entre dois pacotes: os dados de
identificação do usuário residem em \textit{Usuário}, ao passo que as
estruturas que sustentam sessão e redefinição de senha residem em
\textit{Sistema}. O agrupamento em pacotes obedece à afinidade conceitual entre
as classes, e não à organização adotada na especificação dos requisitos.

O modelo de domínio resultante é apresentado na Seção~\ref{sec:modelo_dominio},
ao final deste capítulo, depois de detalhados os requisitos e os casos de uso
que o originaram.


\section{Requisitos do Sistema}

\citeauthorandyear{Sommerville2011} afirma que os requisitos do sistema são tradicionalmente classificados em requisitos \textbf{funcionais}, 
que descrevem as funcionalidades que o sistema deve oferecer, e requisitos \textbf{não funcionais}, que definem restrições de qualidade como desempenho, 
segurança e usabilidade. Eles constituem o núcleo da especificação do sistema, pois delimitam o escopo das funcionalidades a serem implementadas, 
e sua classificação permite uma organização sistemática das especificações, facilitando tanto o desenvolvimento quanto a validação do sistema.

Assim, esta seção apresenta os requisitos identificados neste trabalho, organizados nas subseções a seguir.


\subsection{Requisitos Funcionais}

Segundo \citeauthorandyear{Sommerville2011}, requisitos funcionais descrevem as funções ou serviços que o sistema deve fornecer, ou seja, o que o sistema deve fazer. 
Eles especificam as ações que o sistema deve ser capaz de executar em resposta a entradas específicas ou em determinadas condições.

Os atores que interagem com o sistema são: \textbf{Usuário}, que representa a pessoa cadastrada na plataforma e responsável por criar, editar e gerenciar suas categorias, 
coleções, itens e interações sociais; e o \textbf{Sistema}, que atua de forma autônoma em funcionalidades como exibição de fichas de itens, envio de notificações, 
registro dos eventos que alimentam o feed e organização visual dos dados.

Para padronizar a especificação dos requisitos, adotou-se o verbo \textbf{gerenciar} como forma genérica de representar operações do tipo CRUD (cadastrar, editar e excluir), 
sempre que aplicável. Essa padronização reduz a repetição textual e torna a descrição dos requisitos mais objetiva.

Os requisitos funcionais estão organizados em seis grupos, apresentados de forma sequencial e seguindo uma ordem lógica de dependência entre funcionalidades, 
alinhada à jornada natural do usuário no sistema: iniciam pelo \textbf{Acesso ao Sistema} (cadastro, autenticação, recuperação e alteração de senha e gerenciamento de perfil); prosseguem com a \textbf{Coleção}, núcleo do sistema (categorias, coleções, privacidade, itens, suas fichas e formas de visualização); avançam para o \textbf{Editor de Layout} (criação de layouts, associação a coleções, compartilhamento entre usuários e personalização individual); seguem para a \textbf{Aparência}, camada de personalização visual que se aplica sobre o conteúdo já organizado (paletas de cores e tipografia, com estilo claro ou escuro); contemplam a \textbf{Interação Social} (amizade, acompanhamento de coleções e visualização de perfis); e culminam na \textbf{Notificação}, mecanismo de comunicação de eventos ao usuário.
Os quadros~\ref{quad:descricao_campos} a~\ref{quad:atores} apresentam a definição dos campos e das classificações utilizadas na especificação, e os requisitos funcionais 
identificados para este sistema estão apresentados nos Quadros~\ref{quad:rf01} a~\ref{quad:rf24}.

& \itemrf{3}Toda coleção pertence a exatamente uma categoria. \\

& \itemrf{15}A tag sobrevive à exclusão das coleções que a utilizavam: o vínculo é desfeito, e a palavra permanece disponível no vocabulário. \\
& \itemrf{16}O ícone aceita uma única forma por vez: escolher uma imagem substitui o emoji, e escolher um emoji descarta a imagem. Difere da categoria (RF-06), onde o emoji e a capa coexistem. \\
& \itemrf{17}A imagem do ícone é enquadrada pelo usuário em proporção quadrada antes de ser gravada. O sistema guarda o arquivo original junto com a área recortada, de modo que o enquadramento possa ser refeito depois sem novo envio; remover o ícone apaga as duas imagens. \\ \hline

\begin{quadrolongo}{RF-14 -- Gerenciar Layout Personalizado}{quad:rf14}{RF-14}{Editor de Layout}
\textbf{Descrição}   &
\textbf{Ação:} Gerenciar e duplicar

\textbf{Objeto:} Layout personalizado (template)

\textbf{Atributos:} nome do layout (100 caracteres), descrição (300 caracteres, opcional), fundo da ficha (uma cor hexadecimal, ou um degradê de duas cores com um ângulo e um ponto de início), Elementos disponíveis (conforme os tipos fixos definidos pela enumeração TipoElemento: texto, imagem, forma, ícone, classificação e data), conteúdo textual opcional do Elemento, EstiloDeElemento de cada Elemento (fonte, tamanho, peso, itálico, sublinhado, riscado, alinhamento horizontal e vertical, nível de título, entrelinha, espaçamento entre letras, cor, cor de fundo, arredondamento, opacidade, rotação, borda (cor, espessura e traço), forma do elemento, curva e ponta da linha, ajuste de imagem, apresentação em lista, nota máxima e ícone da classificação, formato e estética da data), camada de sobreposição, posição e tamanho de cada Elemento na área de edição, layout de origem (referência opcional, preenchida apenas na operação de duplicação). \\
& \textbf{Exemplos:} Camila cria o layout `Card de Livro' com Elemento de Imagem para capa, textos livres como `Autor: Frank Herbert', Classificação de 1 a 5 estrelas, dois Elementos de Data (início e fim de leitura) e área de Texto para notas.
Camila reposiciona o Elemento de Classificação via \textit{drag-and-drop} e visualiza o resultado em tempo real na prévia.
Camila seleciona o layout `Card de Livro' e clica em `Duplicar'; o sistema cria `Card de Livro (cópia)' com a mesma estrutura, que Camila renomeia para `Card de Livro -- Edição Especial' e ajusta sem afetar o original.
Camila exclui o layout `Card Antigo' que não está associado a nenhuma coleção.
Para excluir o layout `Card de Série', ainda usado pela coleção `Assistidas', Camila primeiro o desassocia das coleções; os itens que o exibiam sem ficha própria recebem uma cópia dele, e a aparência desses itens não muda. \\
& \textbf{Restrições:} \\*
& \itemrf{1}O nome do layout é obrigatório e deve ser único por usuário. \\
& \itemrf{2}A biblioteca de layouts do usuário reúne três origens: os layouts que ele mesmo cria, os layouts padrão oferecidos pelo sistema desde o cadastro (RF-01) e os layouts importados de outros usuários (RF-16). Todos podem ser igualmente editados, duplicados e associados a coleções. \\
& \itemrf{3}Um layout pode ser gravado sem Elementos, pois a gravação é automática e acompanha cada alteração; o layout vazio pode ser associado a uma coleção e preenchido depois. \\
& \itemrf{4}Os tipos de Elemento disponíveis para inclusão são os definidos pela enumeração TipoElemento (texto, imagem, forma, ícone, classificação e data), à semelhança dos elementos fixos oferecidos por editores visuais como o Canva. \\
& \itemrf{5}Elementos podem armazenar conteúdo visual próprio, como `Autor:' ou `Autor: Frank Herbert', além de propriedades de fonte, cor e alinhamento. \\
& \itemrf{6}Elementos podem ser reposicionados e redimensionados via arrastar e soltar (\textit{drag-and-drop}). \\
& \itemrf{7}O fundo da ficha é escolhido pelo usuário, como cor única ou como degradê entre duas cores, e vale para o layout inteiro, e não para um Elemento em particular. \\
& \itemrf{8}A tinta padrão dos Elementos acompanha o fundo escolhido, por razão de contraste: sobre um fundo escuro, o Elemento que não define cor própria é desenhado em tom claro, e vice-versa. A escolha explícita de cor em um Elemento prevalece sobre esse padrão. \\
& \itemrf{9}Alterações devem ser refletidas em tempo real na prévia do editor, sem recarregar a página. \\
& \itemrf{10}A duplicação deve copiar integralmente a estrutura de Elementos (tipo, conteúdo, estilo, posição, tamanho e propriedades) do layout de origem. \\
& \itemrf{11}Na duplicação, o sistema sugere automaticamente o nome original acrescido de `(cópia)', podendo ser editado antes de salvar. \\
& \itemrf{12}Alterações no layout duplicado não devem refletir no layout de origem. \\
& \itemrf{13}O usuário pode excluir um layout somente se ele não estiver associado a nenhuma coleção nem tiver originado fichas próprias de itens (RF-15 e RF-17). Para os layouts em uso, o sistema oferece a desassociação de todas as coleções que o utilizam: cada item que o exibia sem ficha própria recebe antes uma cópia dele, de modo que nenhuma ficha muda de aparência, e as fichas próprias que dele derivaram deixam de referenciá-lo, sem perder nenhum Elemento. Feita a desassociação, o layout pode ser excluído. \\
& \itemrf{14}A data de criação do layout duplicado é a data da operação, e não a do layout de origem. \\ \hline

\begin{quadrolongo}{RF-15 -- Associar Layout a Coleção}{quad:rf15}{RF-15}{Editor de Layout}
\textbf{Descrição}   &
\textbf{Ação:} Associar

\textbf{Objeto:} Layout (template) a uma coleção

\textbf{Atributos:} coleção de destino (existente, pertencente ao usuário), layout selecionado na biblioteca do usuário (criado por ele, padrão do sistema ou importado de outro usuário, podendo já estar associado a outras coleções). \\

Camila associa à coleção `Mangás' um layout padrão oferecido pelo sistema, por não desejar compor a ficha do zero.
Camila troca o layout da coleção `Mangás' para `Card de Mangá'; antes de confirmar, vê a prévia das fichas próprias levadas ao novo layout e escolhe quais levar; as que não escolheu mantêm sua ficha como estava (RF-17). \\
& \textbf{Restrições:} \\*
& \itemrf{1}Um layout só pode ser associado a coleções existentes e pertencentes ao mesmo usuário. \\
& \itemrf{2}O layout é associado no nível da coleção; a categoria não recebe layout (RF-06). \\
& \itemrf{3}A associação é opcional. O usuário pode escolher qualquer layout de sua biblioteca, seja criado por ele, padrão do sistema ou importado de outro usuário (RF-14 e RF-16); nenhum layout é aplicado automaticamente. \\
& \itemrf{4}Uma coleção pode ter, no máximo, um layout ativo por vez. \\
& \itemrf{5}Um mesmo layout pode ser associado a várias coleções simultaneamente, sendo reutilizado como template. \\
& \itemrf{6}O layout aplicável a um item é o da sua coleção; na ausência de layout associado, a ficha do item nasce vazia e ele pode receber um layout próprio, montado ali mesmo. Modificações individuais por item são tratadas como \textit{override} (RF-17). \\
& \itemrf{7}A troca ou remoção do layout da coleção não altera, por si só, os dados nem os Elementos individuais (\textit{override}) dos itens já cadastrados (RF-17). Os itens sem ficha própria passam a exibir o layout novo. \\
& \itemrf{8}Na troca, o sistema oferece a mescla das fichas próprias com o layout novo, apenas para os itens que o usuário escolher. Cada Elemento da ficha é associado a um Elemento do layout novo pela mesma origem, depois pelo mesmo tipo e nome e, por fim, pelo mesmo tipo na ordem de leitura; do Elemento antigo vem apenas o valor, e a posição, o tamanho e o estilo vêm do layout novo. Os Elementos com valor que não encontram correspondência permanecem na ficha; formas e ícones, que são desenho do molde e não valor do item, não são transferidos. A mescla também pode ser pedida a qualquer momento para um único item, a partir do editor da sua ficha. \\
& \itemrf{9}Antes de confirmar a troca, o sistema exibe a prévia de cada ficha própria levada ao layout novo. \\
& \itemrf{10}O usuário pode remover a associação de layout da coleção a qualquer momento. \\ \hline

\textbf{Operação}    & Entrada \\ \hline
\textbf{Ator}        & Usuário \\ \hline
\end{quadrolongo}

& \itemrf{2}O usuário pode criar, editar, duplicar, renomear e excluir paletas, e selecionar a paleta em uso a qualquer momento. As paletas predefinidas pertencem ao usuário e podem ser editadas e excluídas como as personalizadas. O nome de uma paleta não pode se repetir entre as paletas do mesmo usuário, mas pode coincidir com o de paletas de outros usuários. \\
& \itemrf{3}A paleta em uso deve ser aplicada globalmente a todas as telas do sistema de forma imediata. \\
& \itemrf{4}A paleta em uso não pode ser excluída, o que garante que o usuário tenha sempre ao menos uma paleta. \\
& \itemrf{5}Uma paleta é sempre completa: a cor primária e todas as subcores devem estar preenchidas. Cada superfície (fundo da página, cartões, barra lateral, cabeçalho e modais) tem sua própria cor de texto, escolhida pelo usuário; no estilo em que a paleta foi desenhada, o sistema exibe exatamente a cor escolhida, sem substituí-la, e a única transformação aplicada é a inversão de claridade descrita na restrição 6. \\
& \itemrf{6}O sistema classifica cada paleta como clara ou escura a partir da cor de fundo. Quando o estilo global em vigor é o oposto ao da paleta em uso, as cores são exibidas com a claridade invertida, preservando os tons. \\
& \itemrf{7}As paletas e a paleta em uso devem ser salvas no perfil e persistidas entre sessões e dispositivos. \\
& \itemrf{8}Enquanto o usuário edita uma paleta, a interface exibe a própria paleta em edição, para que ele veja o resultado exato antes de confirmar. Nada é gravado até que ele salve, e cancelar ou sair devolve a interface à paleta em uso. A paleta é exibida no estilo em que foi desenhada; a inversão para o estilo oposto acontece apenas quando ela está em uso (restrição 6). \\
& \itemrf{9}O sistema deve alertar o usuário quando uma combinação de cores não atender ao contraste mínimo (RNF-09), sem impedir a escolha. \\
& \itemrf{10}A biblioteca de paletas pode ser exibida em grade ou em lista e filtrada por paletas claras ou escuras. \\ \hline

\subsection{Requisitos Não-Funcionais}
Segundo \citeauthorandyear{Sommerville2011}, os requisitos não funcionais são requisitos que não estão diretamente relacionados com os serviços específicos oferecidos 
pelo sistema a seus usuários.
Logo, não dizem respeito diretamente às funcionalidades fornecidas pelo sistema, mas sim às suas propriedades e restrições de qualidade.
\citeauthorandyear{pressman2016}, dizem que esses requisitos especificam atributos como desempenho, usabilidade, segurança, confiabilidade e portabilidade, 
sendo fundamentais para garantir que o sistema atenda aos padrões de qualidade esperados.
Assim, esta seção apresenta os requisitos não-funcionais identificados neste trabalho, consolidados nos Quadros de ~\ref{quad:rnf01} a ~\ref{quad:rnf10}.

\subsection{Requisitos Adiados}
\label{subsec:requisitos_adiados}
Alguns requisitos foram identificados durante a elicitação, porém não serão implementados nesta primeira versão do sistema. Eles poderão ser considerados em iterações futuras.

\begin{itemize}
\item Implementação de chat privado entre usuários.
\item Recomendações automáticas baseadas nas coleções dos amigos.
\item Exportação de coleções em PDF ou outros formatos.
\item Mecanismos avançados de descoberta pública, como ranking e tendências. A descoberta simples, que reúne coleções de outras pessoas pelas tags, faz parte do RF-07.
\end{itemize}

Outros três comportamentos chegaram a ser especificados, mas foram retirados dos requisitos
desta versão e ficam registrados aqui, para que a especificação descreva apenas o que o sistema
entregue faz:

\begin{itemize}
\item \textbf{Alteração do e-mail cadastrado} (RF-05). A troca do endereço, com envio de um link
de verificação ao novo e-mail e manutenção do antigo até a confirmação, não está disponível. O
envio de mensagens já existe na plataforma, pois é usado na confirmação do cadastro (RF-01) e na
recuperação de senha (RF-04), e seria o ponto de partida desse fluxo.
\item \textbf{Entrega imediata de eventos ao navegador} (RF-22 e RF-24). O \textit{feed} e as
notificações são atualizados por consulta periódica à API, sem recarregar a página. A entrega
iniciada pelo servidor no instante em que o evento ocorre, por um canal contínuo de comunicação,
fica para uma etapa posterior.
\item \textbf{Ordenação dos Itens pela classificação e filtros pelo conteúdo dos Elementos}
(RF-12). Como a classificação é um Elemento da ficha, e não um campo do Item, ordenar e filtrar
por ela exige consultar o conteúdo das fichas, o que não foi implementado; a listagem oferece as
ordenações por nome e por data e a busca pelo nome e pelo subtítulo.
\end{itemize}

Logo, um caso de uso é uma descrição de um cenário específico de interação entre um ator e o sistema, detalhando as ações realizadas e os resultados esperados. 
Ele é utilizado para capturar os requisitos funcionais do sistema, fornecendo uma visão clara e estruturada das funcionalidades que o sistema deve oferecer.

Uma especificação de caso de uso fornece a descrição textual detalhada do comportamento do sistema a partir da perspectiva do usuário, permitindo compreender 
como as funcionalidades são executadas e quais resultados são esperados. As especificações apresentam os fluxos principais, fluxos alternativos, condições prévias 
e pós-condições associadas a cada interação.

Neste trabalho, foram elaboradas dezenove especificações textuais, cobrindo os casos de uso que possuem fluxo próprio e alternativas relevantes. Os demais casos de uso presentes nos diagramas não receberam especificação por representarem variações, detalhamentos ou funcionalidades já incluídas nos fluxos básicos aqui descritos, como é o caso das operações de edição e exclusão, cujo fluxo espelha o de criação com a diferença do registro previamente selecionado. a~\ref{tab:especVisualizarFeed}, adaptado da IBM.

Cabe destacar a estrutura hierárquica adotada pelo sistema, que organiza os dados em três níveis: \textbf{Categoria} (agrupador temático de alto nível, ex.: ``Livros''),
\textbf{Coleção} (subdivisão de uma categoria onde os itens são efetivamente cadastrados e onde o layout é associado, ex.: ``Lidos'', ``Para Ler'') e \textbf{Item}
(unidade individual de conteúdo, ex.: o livro ``Duna''). Essa separação permite que o usuário organize seu acervo em duas camadas antes de cadastrar qualquer item,
facilitando a categorização e a personalização por meio do layout definido em cada coleção.

    \item O sistema registra a cópia com a finalidade de \textit{template} importado e guarda a referência ao layout de origem.

    \item O sistema exibe mensagem informando que o layout não está mais disponível.
    \item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA02:} Importação do próprio layout
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]

    \item O sistema informa que, para obter outra cópia de um layout próprio, deve-se utilizar a duplicação (RF-14).
    \item O caso de uso é encerrado.
\end{enumerate}

\textbf{FA03:} Nome de layout já existente na biblioteca do destinatário
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]

    \item O sistema dá à cópia o nome original acrescido de ``(cópia)'', ou de ``(cópia 2)'' e assim por diante, como na duplicação (RF-14).
    \item O fluxo continua no passo 10 do FB01; o destinatário pode renomear a cópia depois.
\end{enumerate}

\textbf{FA04:} Alteração posterior no layout de origem
\vspace{2pt}
\begin{enumerate}[nosep,leftmargin=1.2em,topsep=0pt,partopsep=0pt,parsep=0pt,itemsep=0pt,after=\vspace{2pt}]
    \item Após a importação, o proprietário altera ou exclui o layout de origem.
    \item As cópias já importadas permanecem inalteradas, pois são independentes.
    \item Na exclusão, o sistema apenas zera a referência à origem, preservando a cópia.
\end{enumerate}

Condições Prévias & Ambos os usuários devem estar cadastrados. O layout de origem deve existir e pertencer a quem compartilha. Não é exigido vínculo de amizade entre os dois. \\ \hline

Pós-Condições & Uma cópia independente do layout passa a existir na biblioteca do destinatário, utilizável e editável como se tivesse sido criada por ele. O layout de origem permanece inalterado, e nenhum item ou personalização individual do proprietário é compartilhado. \\ \hline

Pontos de Extensão & E01 - Visualizar Prévia do Layout (estende o passo 7 do FB01 -- exibe a estrutura antes de confirmar a importação). \\
